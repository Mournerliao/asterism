# 0029 · AI 整理采用目标优先的任务模型

- Status: Accepted
- Date: 2026-07-28
- Supersedes: ADR 0020 中 selection-first、用户自行分批与逐项审阅的产品形态；ADR 0026 中“系统不主动提示”的绝对产品性格
- Preserves: ADR 0020 的人工授权与 canonical 保护、ADR 0023 的可靠批量账本、ADR 0026–0028 的检索优先与 canonical / derived 双平面

## 背景

现有 AI 整理要求用户先手动选择或构造筛选范围，单次最多处理 50 条，再逐仓库审阅完整建议表。真实用户旅程与 PIM / 主流产品研究表明，这把范围发现、技术分批和大部分审阅劳动留给了用户；提高数量上限不能修复这一范式问题。全库互斥分簇、自动主题体系和二维星图又已被真实个人库验证否定，不能作为替代方案。

## 决策

Asterism 把 AI 整理改为**目标优先的整理任务**：用户表达希望得到的结果，系统利用 derived 元数据、embedding、现有 canonical 关系、时间与状态，从用户授权的完整 Star 库中发现并解释候选范围；手动选择只作为可选的精确上下文，不再是 AI 开始工作的前置条件。Generation 继续使用 BYOK，并在内部按 Provider / 工具安全边界有界分页；`50` 是内部调用约束，不是用户任务上限。

同步后系统可以无 BYOK、无费用地提示少量可忽略的**整理机会**，但只有用户接受某个目标后才能启动 Generation 或形成 canonical 变更计划。首次同步提供一次用途导向的“建立初始秩序”，以后同步主要维护新增内容；两者都不是强制 Inbox Zero。Canonical 分类表达用户未来如何使用收藏，内容相似度只负责发现候选，系统不再声称自动发现全库的天然主题体系。

审阅粒度由风险决定：加入已有分类可按动作组聚合确认并允许排除个别仓库；新分类的名称与代表成员单独确认；移除已有关系独立且更严格地确认；不确定项不操作。每次已执行的 AI 整理任务都必须支持任务级撤销，恢复该任务改变的关系，同时不得粗暴删除后来被用户继续使用的分类。最终写入与撤销都复用持久化批量执行语义，不建立无人值守的 canonical 写入通道。

## 权衡

单纯提高 50 条上限仍要求用户挑批，自动生成全库主题又会把模型推断误当成用户用途，无人值守写入则破坏 canonical 神圣性，因此均不采用。目标优先任务会增加持久状态、费用解释和撤销设计的复杂度，但这些复杂度由系统承担，直接换取大库用户更少的整理劳动，属于本产品应做的难而正确的工作。

## 影响

当前 `ai_organization_drafts`、单活动草稿和 selection-first UI 属于已交付但待替换的旧产品形态。新的任务状态、跨页规划、费用 / 进度披露、撤销账本与具体 UI 由后续真实库原型和规格确定；在此之前不得把内部自动分页暗加到旧契约，也不得直接进入生产 UI 实现。
