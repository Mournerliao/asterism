# 2026-07-28 · 自然 AI 整理一次性原型

## 原型问题

目标优先的整理旅程贯穿“可忽略机会 → 用途目标 → 全库候选解释 → 整体任务 → 风险审阅 → 执行结果 → 任务撤销”时，能否比 selection-first 更少转嫁整理劳动，同时保持 canonical 授权、BYOK 披露与可恢复语义？

## 原型形态

- 在现有 Browse 路由与真实 App Shell 中提供 3 个结构差异明显的开发态方案，通过 `?variant=A|B|C` 切换：
  - A「引导式工作区」：主舞台 + 明确旅程摘要，强调阶段与授权边界。
  - B「规划对话」：目标表达接近助手对话，计划与风险决定在同一时间线展开。
  - C「整理控制台」：机会、当前阶段与任务状态三栏并置，偏向持续维护和恢复。
- `?scenario=first|incremental` 分别覆盖首次同步的 518 条历史大库 / 186 个候选，以及后续同步的 7 个新增 Star。
- 状态仅驻留内存；机会提示、范围发现、Generation、执行与撤销均为 stub，不调用 Provider、不访问真实写入接口，也不修改 canonical。
- 登录态存在时优先展示真实仓库名称；无登录态走查使用 8 个脱敏 / 公开仓库标识作为 fallback。
- 启动命令：`pnpm prototype:natural-ai`。入口 URL 为 `/?prototype=natural-ai&variant=A&scenario=first`，只在开发环境生效。

## 核心问题证据与暂定结论

| 核心问题 | 原型证据 | 暂定结论 |
| --- | --- | --- |
| 整理机会如何不打扰 | 首次同步说“建立初始秩序”，后续同步说“7 个新增 Star 可能适合已有结构”；两者均同时展示忽略入口及“derived / 无 BYOK / 无改动” | 机会适合作为 Browse 内可忽略入口；首次与增量必须使用不同目标与范围语境 |
| 如何表达完整目标 | 三种方案都先展示用途语言 Textarea，技术范围只作为可选链接 | 默认入口无需先选仓库或构造 facet；目标文本应先于范围控制 |
| 如何解释全库候选 | 范围阶段同时展示总候选、确定性依据、代表仓库、排除边界、Provider、字段、截断、整体调用数与费用 | “为什么是这些”与“发送什么 / 做多少”可以在一个任务启动面中表达；50 条无需成为用户操作 |
| 如何按风险审阅 | 加入已有集合按目标聚合并支持 repository 级排除；新集合单独批准名称和代表成员；移除关系使用 destructive 边界、具体关系列表和独立批准 | 审阅主对象应是动作组；只有抽查、排除和移除需要下沉 repository 级 |
| 如何执行与撤销 | 最终计数随排除及审批实时变化；执行后给出任务级撤销，撤销结果明确恢复关系、保留后来继续使用的集合 | 撤销应绑定任务实际成功关系，而不是“删除本任务创建的分类” |

## 浏览器走查

- 桌面端完整走通 A：机会 → 目标 → 186 条候选解释 → 4/4 内部有界步骤 → 排除 1 条 → 批准 1 个新集合 → 批准 3 项移除 → 执行 23 / 1 / 3 → 任务撤销。
- 验证方案切换会更新可分享 URL，且在 A → B → C 之间保留当前内存状态；左右方向键在非输入控件聚焦时可切换。
- 后续同步场景显示 7 个稳定候选与 1/1 内部步骤，不把历史库混入维护任务。
- en / zh-CN locale 测试通过；浏览器确认简体中文界面可达。
- 390 × 844 下 A 安全重排，移动触控入口可用；light / dark 均已截图检查，内容表面与 Graphite Glass 控件边界保持一致。

## 方案判断

- A 当前最适合验证完整授权旅程：阶段、范围与任务状态最容易解释，但若长期常驻可能显得流程化。
- B 最自然地承接用户语言目标，但在复杂审阅和中断恢复时容易把持久任务状态埋进对话。
- C 最适合同时存在多个机会、运行中任务与恢复状态，但作为首次默认入口过重。
- 用户评审选择 **B「规划对话」**，明确理由是“对话形式更自然”。
- 该 verdict 决定后续规格的主交互骨架，但不表示把所有任务状态都做成聊天消息；复杂审阅、长任务进度与恢复仍需稳定、可直接到达的任务面。
- 这是原型偏好验证，不单独形成新 ADR，也不把当前原型实现升级为生产规格。

## 仍未回答

只保留会显著改变规格的问题：

1. B 的对话主骨架应在何处切换到稳定任务面，才能让复杂审阅、运行进度与中断恢复不依赖回看聊天记录。
2. 整体费用预估应给区间、token / 调用工作量，还是 Provider 原币种上限；当前金额仅为原型占位，不能进入规格。
3. 任务运行中暂停 / 结束、部分 Generation 失败与重新规划后，用户看到哪些稳定检查点；本原型只表现完成后的整体状态。
4. 撤销与任务之后的用户关系变更冲突时，精确跳过规则和部分失败反馈；原型只验证“保留后来继续使用的分类”这一产品语义。
